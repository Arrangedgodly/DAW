# FX performance audit

R-01 research report, 2026-09-23. Scope: `src/audio/fx.ts`, `src/audio/mixer.ts`, `src/audio/worklets/mixerLimiter.js`, the bitcrusher in `src/audio/worklets/voiceEngine.js`, and their live/offline wiring. This is a source audit, not a timed benchmark or listening test. No production code or schema changed.

## What the graph does today

`src/document/fx.ts` permits filter, drive, bitcrusher, delay, and reverb, with at most three devices per lane and eight on the master. `FxChainHost` creates even bypassed devices, reconnects around bypassed devices, and rebuilds a whole chain when its type sequence changes (`src/audio/fx.ts:628-709`). Live lane chains enter channel processing before lane gain; the master FX chain enters master compression and limiting (`src/engine/session.ts:1711-1800`, `src/audio/mixer.ts:128-195`). Offline export uses the same FX/mixer builders but a new `OfflineAudioContext` and 44.1 kHz render (`src/audio/render.ts:283-495`). These shared builders are a useful compatibility constraint.

| Processing | Current cost or behavior | Evidence and disposition |
| --- | --- | --- |
| Filter | One native `BiquadFilterNode`; frequency and Q use 10 ms `AudioParam` targets. | `fx.ts:338-365`. Already a small native graph. Keep its sound and automation; no demonstrated benefit from custom DSP. Biquad frequency/Q are audio-rate parameters per [MDN BiquadFilterNode](https://developer.mozilla.org/en-US/docs/Web/API/BiquadFilterNode). |
| Drive | Native `WaveShaperNode` with `2x` oversampling; 1024-point curves cached in 65 amount buckets. | `fx.ts:171-199,368-396`. The cache bounds curve generation. Oversampling reduces aliasing but changes cost and response per [MDN WaveShaper oversample](https://developer.mozilla.org/en-US/docs/Web/API/WaveShaperNode/oversample). Do not lower it on a performance hunch. |
| Bitcrusher | A separate `AudioWorkletNode` for each instance; parameter edits send a port message. Processor computes `levels` once per block and holds stereo samples for `downsample` frames. | `fx.ts:399-424`, `voiceEngine.js:465-521`. Its loop is simple. A worklet remains necessary for its hold state; batching or moving it into voices changes ordering and needs audio parity evidence. |
| Delay | Native 2 s `DelayNode`, feedback loop, damping biquad, dry/wet gains. `syncBpm` still reads constructor `timeSteps` after edits. | `fx.ts:428-491`. The stale time setting is assigned to P-02. Preserve the 15 ms glide and hard update semantics. Native `DelayNode` represents intentional signal delay; reducing that is a musical change, not output latency optimization. |
| Reverb | Native `ConvolverNode`; every instance renders a seeded stereo IR of 0.7 to 1.5 s and copies it into an `AudioBuffer`. Size changes compare against constructor size, so later mix edits after a size edit regenerate the IR. | `fx.ts:82-121,493-553`. The repeated regeneration fix belongs to P-02. At 44.1 kHz the two raw float arrays hold about 247 to 529 KiB before the `AudioBuffer` copy. `normalize=false` is intentional; [MDN Convolver normalization](https://developer.mozilla.org/en-US/docs/Web/API/ConvolverNode/normalize) says normalization takes effect when setting the buffer. Cache/worker alternatives need memory and parity measurements. |
| EQ | Every channel processor constructs eight biquads and three gain nodes per slot, plus global dry/wet/output gains, regardless of enabled bands. Legacy EQ maps to four bands; explicit EQ allows eight. | `mixer.ts:80-127`, `document/mixer.ts:88-116`. For eight channels this is 64 biquads and 192 slot gains at graph creation, even if all EQ is disabled. This is a node count, not a measured CPU cost. The existing parallel dry/wet slot topology keeps edits connected but deserves a targeted graph-cost test. |
| Compression | Every channel and master creates one compressor worklet with dry/wet routing; disabled processing copies samples and resets state. Enabled processing uses per-sample peak detection, `log10`, `pow`, smoothing, and linked stereo gain. | `mixer.ts:47-79`, `mixerLimiter.js:66-154`. A disabled compressor still receives the connected wet input. The power/log calls are a plausible live-load target, but coefficient or detector changes can alter transients. Preserve the 6 dB knee and explicit makeup. |
| Limiting | The master keeps the legacy soft-clip branch and worklet limiter branch connected. Gains choose the audible branch. Limiter calculates stereo peak and release per sample, and sends reduction every 32 blocks. | `mixer.ts:128-195`, `mixerLimiter.js:1-63`. Muting a branch does not prove the browser stops upstream processing. Disconnect/reconnect might reduce work but risks clicks and state changes. The limiter is zero-lookahead sample-peak, with no true-peak promise. |
| Chain host | Every same-type `setChain` call tears down and reconnects active edges, even for a parameter edit; changed references call `setParams`. Type-sequence changes rebuild all devices, including bypassed ones. | `fx.ts:628-709`. Reconnect frequency is a control-thread cost and possible glitch risk. An identity/parameter/bypass fast path would be narrow, but needs topology and audible-edit tests. |

## Keep the latency questions separate

| Question | Current path and useful measurement | What the source supports |
| --- | --- | --- |
| Startup and bundle latency | `createVoiceEngine` loads the voice/bitcrusher module, then `prepareMixer` loads the compressor/limiter module before live routing (`voiceEngine.ts:185-204`, `session.ts:1857-1901`). Measure first gesture to first audible note, separately from JS download/parse and `addModule`. | [`addModule()`](https://developer.mozilla.org/en-US/docs/Web/API/Worklet/addModule) resolves after a module is added. Combining modules might save a load request, but changes cache and initialization behavior; measure before doing it. |
| UI and control work | `setMixer` updates every existing channel; same-sequence FX updates relink edges. `readMixerSpectrum` allocates a right-channel `Float32Array` on each call (`session.ts:1554-1569`). Measure edit responsiveness and allocation count without running audio benchmarks concurrently. | These costs are on the control/UI path. A reused spectrum scratch buffer is a small, low-risk slice. |
| Offline throughput | `renderProjectToBuffer` builds a new graph, renders, copies raw/stem channel arrays, and folds tails (`render.ts:283-580`). Measure setup, `startRendering`, and postprocessing separately. | [`OfflineAudioContext.startRendering()`](https://developer.mozilla.org/en-US/docs/Web/API/OfflineAudioContext/startRendering) renders the configured graph to a buffer. Faster offline render does not establish lower live load. |
| Live processing load | Worklets run synchronously on the rendering thread for each render quantum. Compare graph configurations on target devices while playing, with glitches/underruns and audio parity, not only an offline stopwatch. | [MDN `AudioWorkletProcessor.process()`](https://developer.mozilla.org/en-US/docs/Web/API/AudioWorkletProcessor/process) documents the render-thread callback and variable block-size caution. The code uses `output[0].length`, which is appropriate. |
| Hardware output latency | `src/audio/context.ts:18-20` requests 44.1 kHz without a `latencyHint`. Measure browser-reported `baseLatency` and `outputLatency` on the active device and, if needed, a physical loopback. | The [Web Audio spec](https://webaudio.github.io/web-audio-api/#dom-audiocontext-baselatency) excludes graph and downstream hardware portions from `baseLatency`; [`latencyHint`](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/AudioContext) is a request browsers may ignore. An FX throughput win alone does not prove lower output latency. |

An adjacent, uncommitted `docs/dev/audio-engine-benchmark.md` reports one Chrome/Windows comparison with Elementary's offline convolver: 158.8 ms median native versus 111.4 ms Elementary for a 9.22 s output. Its first-block mismatch makes the current audio parity comparison invalid. This is another thread's provisional artifact; I did not run or modify it. It supports a follow-up harness diagnosis, not an engine replacement or live latency claim.

## Ranked bounded work after P-02

Ranking combines certainty of the code finding, likely user benefit, and sound/compatibility risk. It does not imply measured speedups.

1. **Reuse mixer spectrum scratch storage.** `Session.readMixerSpectrum` creates a right-channel array for every read (`session.ts:1554-1569`), while `MixerPage.tsx:223` polls it. Benefit: remove repeat UI allocations; low sound risk because only meter data changes. Test selected-lane/master switching, changing output buffer lengths, closing/reopening Mixer, and left/right max-bin parity. Profile allocations to establish whether it matters. Owner: a UI/control PR.
2. **Avoid unnecessary chain relinks on parameter-only edits.** Keep `FxChainHost`'s device order, bypass routing, ramps, and seeds; call `setParams` for changed instances without disconnecting unchanged edges. Benefit: fewer control-thread graph mutations during knob drags, with possible edit smoothness gain. Risk: medium; bypass and structural edits must still relink/rebuild, and param objects can change by identity. Test each device knob, bypass toggles, reorder/add/remove, tail persistence, and live/offline parity. Owner: FX host PR, separate from P-02.
3. **Measure then trim default mixer graph construction.** Eight EQ slots per channel and channel compressor worklets are created even for default disabled processing. A prototype may defer disabled nodes or bypass complete disabled processors while preserving an 8 ms transition and state behavior. Benefit: potentially lower startup and live graph work across eight channels. Risk: high for phase, transient timing, first activation, and offline parity. Start with node-count/setup profiling and A/B renders before choosing a topology. Owner: mixer graph PR only if measurements justify it.
4. **Isolate compressor worklet arithmetic.** Profile enabled compressor blocks before attempting a mathematically equivalent fast path or coefficient caching. Benefit: possible live CPU saving with many enabled channels. Risk: high because peak envelope, knee, gain smoothing, and reduction meter are audible/visible contracts. Test sample-level reference vectors for threshold crossings, attack/release, stereo link, enable toggles, and offline/live output tolerance on target browsers. Do not swap in `DynamicsCompressorNode` without proving its transfer curve matches.
5. **Consider reverb IR reuse only after P-02 and measured edit cost.** A cache keyed by seed, size, and sample rate could avoid duplicate IR work on chain rebuilds; size is a continuous value and seed depends on chain position (`fx.ts:708-735`), so hit rate and memory retention are uncertain. Benefit: edit/setup time, not necessarily per-sample convolution load. Risk: medium memory growth and buffer lifetime; keep deterministic bytes and `normalize=false`. Test two-channel output equality, size/mix edits, reorder, disposal, and memory ceiling.
6. **Evaluate silent master branches and bitcrusher lifecycle with live evidence.** The master runs both clip and limiter paths; the bitcrusher always returns `true` from `process()`. A measured topology/lifetime change may save live work, but signal continuity, limiter release, and bypass behavior are at risk. Compare enabled/disabled and bypass configurations on device, then run click and parity checks before an implementation PR.

P-02 already owns the reverb size comparison and delay tempo-sync stale-setting fixes. Do not fold those into the slices above. Keep `src/document/fx.ts` and `src/document/mixer.ts` compatible with saved projects. Preserve seeded IRs, musical delay timing, drive oversampling, bitcrusher quantization, EQ response, compressor makeup, limiter ceiling, and export tail semantics unless a separate audible product decision approves a change.

## Validation and source limits

This audit checked source and official Web Audio documentation; it ran no benchmark, automated test, browser audition, or device loopback. The provisional Elementary result is offline only and has a known onset mismatch. Native `ConvolverNode`, `BiquadFilterNode`, `WaveShaperNode`, and `AudioWorklet` remain the baseline. The [Web Audio convolution architecture note](https://webaudio.github.io/web-audio-api/convolution.html) describes a low-latency partitioned native approach, but actual browser implementation and Bitbounce workload still require measurement. No source here establishes that replacing the engine improves Bitbounce's live audio or compatibility.
