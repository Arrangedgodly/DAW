# FX benchmark diagnosis (R-02, 2026-09-23)

## Decision

The current `docs/dev/audio-engine-benchmark.ts` is useful as a prototype, but its 61.07% full-output error and 29.8% render-time advantage are not a parity-qualified engine comparison. Two different startup envelopes dominate the signal comparison. Repair the harness before using either number for an engine decision. Keep the production reverb as the reference for its actual behavior, and add a separate fixed-gain reference for convolution parity.

This is research and a P-01 implementation contract. I did not edit or run the benchmark, production code, packages, or a timed workload. The local probes below used only the installed Elementary public API in short, read-only Node sessions.

## What the installed code does

- Installed versions: `@elemaudio/offline-renderer` 4.0.3 and `@elemaudio/core` 4.0.1. The offline renderer's `process(inputs, outputs)` copies each input block into native input storage **before** `_native.process(blockSize)`, then copies native output into the caller's output arrays. Missing sample-zero output is not an input-copy ordering error. Its default block size is 512 (the benchmark does not override it).
- `OfflineRenderer.render()` delegates to `Renderer.render()`. The installed core's default `render()` calls `renderWithOptions({ rootFadeInMs: 20, rootFadeOutMs: 20 }, ...)`. The offline renderer exposes `render`, not `renderWithOptions`, in its public type surface. The graph root therefore fades in over 882 samples at 44.1 kHz. Use the public `process` API to advance that fade; do not reach into `_renderer` or the WASM runtime.
- `el.in({ channel })` takes the corresponding input channel, and `el.convolve({ path }, x)` reads its IR from the virtual file system. The benchmark supplies the same deterministic left/right IR arrays that `createReverbDevice` generates, and native sets `ConvolverNode.normalize = false` **before** assigning the buffer. This is the correct IR normalization order. A stereo native convolver with a two-channel IR is the appropriate channel-wise comparison to two Elementary mono convolvers; confirm with isolated stereo probes.
- Production `createReverbDevice` creates wet and dry `GainNode`s with default gain 1, then calls `setTargetAtTime(mix, currentTime, 0.01)` and `setTargetAtTime(1 - 0.5 * mix, currentTime, 0.01)`. At 50% mix, the targets are 0.5 wet and 0.75 dry. The benchmark's Elementary graph uses those **target constants immediately**. The Web Audio automation approaches targets exponentially, so the production native startup is a different signal even after Elementary's root fade is repaired.

Primary references: [Elementary offline renderer API](https://www.elementary.audio/docs/packages/offline-renderer), [Elementary core renderer options](https://www.elementary.audio/docs/packages/core), [Elementary `el.convolve`](https://www.elementary.audio/docs/reference/convolve), [Web Audio ConvolverNode and channel/normalization contract](https://webaudio.github.io/web-audio-api/#ConvolverNode), [Web Audio `setTargetAtTime`](https://webaudio.github.io/web-audio-api/#dom-audioparam-settargetattime) and [MDN explanation of its time constant](https://developer.mozilla.org/en-US/docs/Web/API/AudioParam/setTargetAtTime). Local implementation evidence: `node_modules/@elemaudio/offline-renderer/dist/index.js` (`render`, `process`), `node_modules/@elemaudio/core/dist/index.js` (`Renderer.render`), and `src/audio/fx.ts` (`renderImpulseResponse`, `createReverbDevice`). These source observations are specific to the installed versions.

## Read-only probe evidence

Using one input/output channel, `blockSize: 512`, and `el.in`, an impulse at sample 0 yielded 0; at sample 512 it yielded 0.5804988742 at sample 512; at sample 1024 it yielded 1 at sample 1024. The same results occurred through `el.convolve` with a unit-impulse IR. The interrupted probe also observed a constant-one root starting at 0 and reaching 1 at sample 882. These observations fit a 20 ms root fade; they do not show a one-block input delay. The earlier 0.290249 value at sample 512 is consistent with the 0.580499 root gain followed by the benchmark's 0.5 wet gain.

After `render`, processing 1024 zero samples into a disposable 1024-sample output made impulses at sample 0, 512, and 1024 pass at unity in both dry and convolved graphs. With IR `[1, 0.5, -0.25]`, the output of a primed graph given an impulse at its next sample 0 matched a fresh graph given an impulse at sample 1024, shifted back 1024 samples: maximum sample difference 0 over 2048 compared samples. The silent prime generated no signal. A subsequent `process` call did not mutate the previous output array, and the input impulse array remained unchanged. This verifies the proposed sequence for a short IR, not browser parity for the benchmark's full IR.

## P-01 repair contract

1. **Make each render self-contained.** Pass immutable input arrays as arguments; return newly allocated output arrays. Do not switch a module-level `input` between full, dry, wet, and delayed probes. Use a fresh native context and fresh Elementary renderer for each measured pass or clearly reset state. Keep the seeded IR and sample rate identical. Assert channel lengths, output length, finite samples, and left/right identity where expected. Bound writes in `makeInput` so a future shorter program cannot silently truncate transients.
2. **Prime Elementary after graph render.** `await core.render(...)`, then `core.process([zeroL, zeroR], [discardL, discardR])` with exactly 1024 samples per channel (two 512-sample blocks), then process the real input from sample zero into the real output. The prime is silence, not a crop of the actual signal; preserve and compare every real program sample and the tail. Label 1024 as a version-specific safe margin beyond the observed 882-sample fade. Assert the priming output is silent and verify a sample-zero dry impulse passes. Do not rely on private fade APIs.
3. **Separate parity questions.** For *renderer parity*, compare (a) native direct wire vs primed `el.in` for dry, (b) native `ConvolverNode` with the same stereo IR, `normalize=false`, and a constant 0.5 gain vs primed Elementary `el.convolve` with 0.5, and (c) a native explicit dry/wet graph with fixed 0.75 dry and 0.5 wet gains vs the matching Elementary graph. Do not call the current native direct-wire dry probe the production device's dry branch. For *production startup*, render actual `createReverbDevice` from time zero and report its first 50-100 ms separately. If comparing to Elementary there, apply the same 10 ms target envelope to Elementary or compare against a reference assembled from separately captured native dry/wet outputs with the scheduled gains. Do not interpret the intentional startup envelope difference as convolution error. Do not discard the initial real transient to improve a parity statistic.
4. **Use discriminating signals and metrics.** Verify dry impulses at 0, 512, and 1024 with exact index and amplitude; add left-only and right-only impulses to reveal channel swaps/crosstalk. For wet, use the seeded full IR and compare the first nonzero samples, peak-error index, full-tail relative RMS and absolute peak, plus a small deterministic vector (or tolerance) over the whole output. Include all channels and all output frames; inspect a few windows rather than relying only on an aggregate. Compare full output against the independently constructed fixed-gain reference. Report startup and settled windows separately, but keep a whole-signal error. If settled error remains material, investigate convolution numerics, partitioning, scaling, and alignment with the probes before setting acceptance tolerances; do not time-shift or gain-fit the outputs to force parity.
5. **Make timing apples-to-apples and disclose scope.** The current native timer surrounds `startRendering()` while Elementary's surrounds only `process()`. Both exclude graph setup, IR generation, and buffer allocation, but native is asynchronous and Elementary copies input/output across WASM synchronously. State these inclusions explicitly and show raw per-pass times as well as medians. Run engines sequentially, alternate order, and run dry/wet diagnostics outside the measured passes; do not use `Promise.all` for render diagnostics. For a settled production-device throughput comparison, schedule native source after a block-aligned silent pre-roll long enough for its 10 ms gain targets to settle (for example 4096 samples, about 92.9 ms) and process the **same** silent pre-roll through Elementary before real samples. Either time both entire pre-roll-plus-program renders and divide by the same rendered duration, or publish separately named full-render and processing-only timings; never hide pre-roll cost in only one engine. Crop only the silence from parity arrays, with original signal sample zero retained. A separate cold-start run should preserve actual time-zero signal and report its behavior. The fixed-gain parity topology is diagnostic; the production-device timing must use `createReverbDevice`.
6. **Keep provenance.** Record browser/version, OS, sample rate, IR length, block size, pass count, total rendered frames, warm-up rules, and whether a browser tab was foregrounded. Show `baseLatency` and `outputLatency` only as browser-reported device-context metadata. Offline wall time is throughput, not DSP CPU load, render-quantum deadline success, or physical latency.

Acceptance for P-01: sample-zero dry impulse survives priming with no offset; dry stereo parity is exact or within a justified float tolerance; wet/full fixed-gain differences are quantified over all frames and explained before calling them parity; production startup and settled results are labeled separately; timings use equal rendered windows and no concurrent timed load; browser run includes full output/tail evidence and reproducible environment details. A numerical tolerance must follow measured implementation behavior and desired audio quality, not be widened just to pass.

## Current benchmark pitfalls beyond the startup fades

- The documented first-half-second comparison is a diagnostic window, not a general latency or block-alignment finding. Moving the first transient to sample 512 simply moves it into the fade.
- `compare().laterBeats` averages per-beat relative-error ratios without weighting by reference energy; near-silent beats can dominate. It also stops at eight input seconds and excludes the IR tail, whereas `relativeRms` includes the tail. Report explicit window bounds and use energy-weighted aggregate numerator/denominator for any grouped metric.
- The full comparison uses only the last measured pass per engine. Keep the parity probe deterministic and separate from timing passes, or verify hashes/metrics across passes. The current report's median times describe one Chrome 153 Windows run and cannot be generalized.
- Native `startRendering()` returns an `AudioBuffer`; Elementary `process()` writes to caller-owned arrays. The existing timers exclude native `getChannelData` and Elementary output allocation, and include Elementary's JS/WASM block copies. Preserve these distinctions in labels; if end-to-end UX is relevant, add a separate measurement that includes setup and transfer for both.

## Live follow-up after P-01

Repeat on target browsers/devices. For any engine-selection proposal, instrument the actual Elementary `AudioWorklet`/web renderer and production Web Audio FX chain under the same project workload, including graph creation, parameter updates, bypass, disposal, memory growth, glitches/underruns, and lane/master routing. Confirm live/offline audio parity and audition the result. Neither this research nor offline throughput establishes live safety or listening quality.
