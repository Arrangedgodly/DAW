## Attribution and acceptance

R-03's one short headless window found visualizer callback p95 5.6 ms versus Grid 0.4 ms, without attributing functions. P-06's sampled visualizer profile placed 263 CPU samples under `compositionEngine.ts`, 32 under timbre/listening, and three under other visualizer code. This establishes draw code as material sampled CPU work, not an exact elapsed-time or GPU allocation.

The first baseline/candidate files (`viz-frame-baseline.json`, `viz-frame-contour-reuse.json`) overlapped P-05 browser audio checks and a build. They are retained locally and **excluded from the speed comparison and PR artifact**. After the manager confirmed an idle host, I verified the source was at the base draw implementation, ran the baseline, applied the candidate, and ran it sequentially. Both exited 0 in 23.5 and 23.1 seconds. Their raw outputs were losslessly compressed in the PR as `viz-frame-baseline-clear.json.gz` and `viz-frame-contour-reuse-clear.json.gz`. Browser: Headless Chromium 151.0.7922.34, Windows `win32/x64`, 1280 × 720 through Vite, revision field `a292f3d...` (the candidate was an uncommitted working-tree edit).

The median p95 difference is about 3.6%, below the required 25%. The candidate's measured dropped-interval ratio was higher, so it also lacks no-worse cadence evidence. The fixed eight-lane frame hashes `3372253067`, `3672592734`, `2858053307`, `3234583933` matched before and after the candidate. These data support a **no-change conclusion**, not a production speedup. Song-time and machine drift remain possible in short sequential windows; they add uncertainty rather than evidence for the required gain.
