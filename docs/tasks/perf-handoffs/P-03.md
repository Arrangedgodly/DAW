# P-03: Mixer spectrum polling allocation

**Status:** Complete; PR open and linked to the worker thread.

## Change

`Session.readMixerSpectrum` now retains one private right-channel `Float32Array` scratch buffer per session/output length, reuses it across selected lane/master changes, replaces it when output length changes, and clears it when mixer taps are released. The caller's output remains independent; stereo per-bin maximum behavior, missing-meter `-Infinity` fill, and sample-rate return are preserved.

`MixerPage` still creates a fresh 2048-bin output array on each signal update. This preserves Solid signal update behavior.

## Acceptance and scale

The baseline source at `27acaec` constructs `new Float32Array(out.length)` on every `readMixerSpectrum` call. For the 2048-bin, 80 ms mixer poll this is 8192 bytes per poll, approximately 100 KiB/s of short-lived typed-array allocation traffic per open Mixer page. This is source-derived, not a timed benchmark. The result is a modest UI allocation reduction; no lower audio processing or device output latency is claimed. No timed browser benchmark or audio audition was performed.

Four focused unit tests cover stereo maxima and sample rate, missing-meter fallback, same scratch buffer reuse across selected-meter changes after warm-up, caller-output independence, scratch resize for changed output length, and scratch cleanup on meter release.
